# 功能规格：审批到安全模拟处置

**功能分支**：`002-approval-safe-simulation`

**创建日期**：2026-09-23

**状态**：v1.1 规格修订已确认（2026-09-23）；计划已确认，入口隔离条款同步修订（2026-09-23）

**输入**：SPC-001 第二份独立规格；遵循已批准的 DEC-008 至 DEC-013、DEC-017 至 DEC-020，以及 Spec A v1.0 已确定的 Incident 语义。

## 范围与价值

值班人员能够在已有 Incident 上提出一个明确、安全的模拟处置 Action，经有权限的人员确认后，由服务端独立调度一次执行，并看到可信的结构化结果、审计过程和不确定结果的收敛路径。未获批准、已过期或被篡改的请求不得产生模拟副作用。本规格只交付一个专用安全演示工具，不接入真实服务器、Kubernetes、数据库或云资源处置。

本功能以 Spec A 产生的稳定 `incidentId`、Incident 主状态与只追加 Timeline 为输入；不改变 Spec A 的告警接入、聚合和 Incident 状态规则。Action 状态独立于 Incident 主状态；Action 完成不自动解决或关闭 Incident。

## 用户场景与测试（必填）

### 用户故事 1 - 创建并审批模拟处置（优先级：P1）

值班人员为已有 Incident 提出目标明确的模拟处置；审批人看见不可变的工具、目标与参数摘要后批准或拒绝。批准前没有执行许可，拒绝或过期后不能通过旧确认卡恢复执行。

**优先级理由**：人工授权是所有副作用的前置安全边界。

**独立测试**：在预置 Incident 与安全演示工具定义下，创建 Action、重复提交、批准、拒绝和过期；验证权威审批事实与 Timeline，而不启动工具。

**验收场景**：

1. **Given** 一个允许提出模拟处置的 Incident，**When** 有权限的操作者提交有效提议，**Then** 系统创建 `PENDING_APPROVAL` Action，保存不可变绑定与独立的待审批事实，并显示到期时间。
2. **Given** 相同 Incident、来源类型与来源请求 ID 的提议已被接受，**When** 因响应丢失重复提交相同规范内容，**Then** 返回原 `actionId`，不新建 Action；绑定内容不同则报告冲突。
3. **Given** 待审批 Action 仍有效，**When** 具备审批权限的人批准，**Then** 批准人取自已认证会话，Action 进入 `APPROVED`，执行授权窗口与绑定摘要固定，尚不直接执行。
4. **Given** 待审批 Action，**When** 审批人拒绝或有效期届满，**Then** Action 分别进入 `APPROVAL_REJECTED` 或 `EXPIRED`，旧卡片和迟到批准不能重新授权。
5. **Given** 已批准 Action，**When** 工具、目标或参数需要变更，**Then** 原 Action 不变；必须创建新 Action 并重新审批。
6. **Given** Agent 确认卡被伪造或重放，**When** 没有 Incident 权威审批事实，**Then** 不会签发执行许可，也不会改变模拟目标。
7. **Given** Incident 在 Action 待审批、已批准或票据待消费期间转为 `CLOSED`，**When** 审批、调度或票据消费随后到达，**Then** 不再批准或启动执行，未消费的执行许可失效，Action 与审批事实按原状态记录可审计的过期结果。

### 用户故事 2 - 一次性授权执行安全演示工具（优先级：P2）

获批 Action 在有效窗口内自动调度。工具执行前需同时证明服务身份、有效审批和一次性票据与请求的完整绑定；操作者能区分已成功、明确失败、执行前拒绝和结果未知。

**优先级理由**：这是纵向链路的安全执行与可解释结果核心。

**独立测试**：预置有效批准 Action，驱动调度与安全演示目标；使用正常、篡改、无票、重放和不同调用入口验证单次启动及结构化回执。

**验收场景**：

1. **Given** 有效 `APPROVED` Action，**When** 调度领取成功，**Then** 恰好建立一个逻辑 Execution、一个稳定执行幂等键和一个有效的一次性票据，Action 进入 `DISPATCHING`。
2. **Given** 已认证服务携带有效票据且完整绑定一致，**When** 票据首次被消费，**Then** Action 进入 `EXECUTING`，记录执行开始与回执截止时间，模拟工具最多启动一次。
3. **Given** 缺少服务身份、票据无效或工具/目标/参数/幂等键不匹配，**When** 从任意入口请求受保护工具，**Then** 在副作用前拒绝；未认证请求不得利用自报 `actionId` 终结 Action。
4. **Given** 票据已消费，**When** 同一请求或旧 Agent 确认再次到达，**Then** 返回可关联的重复结果或当前状态，不再次执行模拟副作用。
5. **Given** 工具返回明确结果，**When** 结构化回执到达，**Then** Action 依回执进入 `SUCCEEDED`、`FAILED` 或合法的 `EXECUTION_REJECTED`；自然过期仍使用 `EXPIRED`，不混同拒绝。
6. **Given** 同一回执经服务回调和主应用响应两条路径到达，**When** 重复提交，**Then** 只形成一份权威结果和相应 Timeline 事实；冲突终态不会覆盖既有结论。
7. **Given** 旧 MCP 入口存在尚未纳入 Incident 审批链的写工具，**When** MVP 启动并从旧入口、工具发现路径或直接工具名调用，**Then** 这些工具不在可执行注册表中，调用不能产生副作用；经核查的只读工具仍可使用。

### 用户故事 3 - 故障恢复与 UNKNOWN 证据收敛（优先级：P3）

Worker 崩溃、网络中断或工具超时后，系统不能猜测处置失败并重试副作用；值班人员能看到 `UNKNOWN` 原因、只读对账和有证据的人工结论。

**优先级理由**：不确定执行是最容易造成重复副作用和虚假成功的故障窗口。

**独立测试**：预置 `DISPATCHING` 或 `EXECUTING` Action，注入票据丢失、消费竞争、超时、回执丢失和迟到结果，验证不重复执行及最终可审计收敛。

**验收场景**：

1. **Given** Worker 崩溃且票据明文丢失，Action 仍在授权窗口内且没有已消费票据，**When** 恢复处理，**Then** 原票据失效、同一 Execution 取得替代票据；任一时刻最多一个有效待消费票据。
2. **Given** 原票据已被消费，**When** 恢复 Worker 与迟到请求并发，**Then** 不签发第二个可执行票据，不再次启动工具。
3. **Given** 工具超时且有可验证的未开始或回滚证据，**When** 评估结果，**Then** 记录证明与安全失败码，Action 为 `FAILED`；证据不足时立即为 `UNKNOWN`，不得乐观失败。
4. **Given** `EXECUTING` Action 超过 `receiptDueAt` 且无确定终态回执，**When** 清扫处理，**Then** 转入 `UNKNOWN`、记录原因并触发只读对账，不重复调用写工具。
5. **Given** `UNKNOWN` Action，**When** 完整绑定的迟到回执或只读对账证明已应用/未应用，**Then** 分别收敛为 `SUCCEEDED`/`FAILED`；无法证明时保持 `UNKNOWN`。
6. **Given** 自动证据无法判定，**When** 具备专门权限的人员提交原因和可核查证据，**Then** 可以将 `UNKNOWN` 收敛为确定结果并追加 Timeline；相反结论须告警并待人工核查，不覆盖终态。
7. **Given** 票据已消费且 Action 为 `EXECUTING`，**When** Incident 随后转为 `CLOSED`，**Then** 已开始的执行仍按回执、截止时间和证据规则结束或收敛，不因关闭而被认定为未执行，也不再次启动工具。

### 用户故事 4 - 查询、会话恢复与可复现验收（优先级：P4）

操作者能以 Action 为主线查看审批、执行、票据结果和原因；Agent 重启后只查询权威 Action 状态，不再发起原写工具；验收人员能复现安全及恢复证据。

**优先级理由**：让安全规则对人可见且可验证，不引入额外 UI 平台。

**独立测试**：预置各 Action 状态，重启 Agent 会话并查询 `actionId`，核对 Timeline 和证据目录；不依赖实时推送。

**验收场景**：

1. **Given** Agent 会话中断后恢复，**When** 按 `actionId` 查询 Action，**Then** 终态结束等待，非终态展示进度；`APPROVED` 的执行仍只由调度流程负责。
2. **Given** 原聊天消息或确认卡丢失，**When** 人员查询 Incident，**Then** Action、审批、Execution、回执和只追加 Timeline 仍能独立解释处置历史。
3. **Given** 可复现验收环境，**When** 执行正常、伪造、重放、消费竞争、超时、回执丢失和对账场景，**Then** 每个场景都有请求标识、最终状态、模拟目标变化和审计事实可核对，秘密不进入证据。
4. **Given** 审批决定或权威回执已经生效，**When** 领域事件发布失败后恢复或重复投递，**Then** 原 Action 结论和 Timeline 保持不变，待发布事件以同一稳定身份重试，Spec A 原有事件语义不变。

### 边界情况

- 在待审批有效期与批准同时到达时，只有一个合法状态转换胜出；迟到操作不能撤销过期。
- Incident 关闭与审批、调度或票据消费并发时，以持久化胜出的状态顺序判定：关闭先胜出则不得再开始执行；票据消费先胜出则保留已开始执行的回执和 `UNKNOWN` 收敛路径。
- 在批准授权窗口结束前签发、但票据有效期延伸超过授权窗口时，票据以较早的授权截止时间失效。
- `DISPATCHING` 时旧票据被替换后迟到，不得消费或把仍持有效替代票据的 Action 错误终结。
- 消费前网络错误仅在仍能证明同一票据待消费且调用方仍持明文时允许有限重试；票据状态不可查即停止自动派发。
- 消费后进程崩溃、响应丢失、回执解析或关联失败，均不能被视为“未执行”。
- 先收到清扫产生的 `UNKNOWN`，再收到确定的迟到回执，允许按证据收敛；终态冲突只能告警。
- 只读对账本身失败或给出不确定结果时保持 `UNKNOWN`，不转成 `FAILED`。
- 未经认证的票据请求、回执或人工结论不得凭所附标识更改 Action。
- 旧 MCP 工具仅凭 `readOnlyHint` 自报只读或 Agent 确认卡不能作为服务端授权；未经核查的工具不得因新增注册自动进入 MVP 可调用清单。
- 模拟目标在相同幂等键下的重复请求不得重复改变；不同 Action 必须重新审批。

## 需求（必填）

### 术语与共享边界

- **Incident**：Spec A v1.0 的权威事件，使用相同 `incidentId`、主状态和只追加 Timeline；本功能不得绕过 DEC-018 的 Incident 状态转换。
- **Action**：一次不可变的拟议副作用操作，具有稳定 `actionId`，从属于一个 Incident。`UNKNOWN` 为未决状态，不是“未执行”或可自动重试许可。
- **逻辑 Execution**：一个 Action 的唯一执行身份，具有稳定 `executionId` 和执行幂等键；替换票据不产生第二个逻辑 Execution。
- **模拟目标**：与真实基础设施隔离、可持久观察状态且可只读核对的专用演示资源。
- **可信时间**：审批、票据、状态转换和执行截止所用的服务端持久化可信时钟；客户端自报时间仅作诊断信息。
- **P0**：本项目第一条可验收纵向链路阶段，不是本规格用户故事优先级 P1～P4。

### 功能需求

- **FR-001**：系统 MUST 只允许在已存在、当前未 `CLOSED` 的 Incident 上提出本功能的 Action；Action MUST 保存稳定 `incidentId` 与操作者/来源引用，且不能改变 Spec A 的告警关联结果。
- **FR-002**：P0 MUST 仅允许一个已登记的安全模拟处置工具及其明确版本、模拟目标与参数契约；真实基础设施目标和未登记写工具 MUST 被拒绝。
- **FR-003**：Action 提议 MUST 由有权限的用户或已认证的受控来源发起，并以 `incidentId + sourceType + sourceRequestId` 去重；相同身份且相同规范绑定返回原 Action，绑定不同返回冲突，不得创建第二个 Action。
- **FR-004**：Action MUST 固定工具名与版本、由服务端确定的目标类型及 ID、规范化参数、版本化绑定摘要和每 Action 唯一的执行幂等键；任一绑定项变更 MUST 创建新 Action 并重新审批。
- **FR-005**：Action 初始为 `PENDING_APPROVAL`；其审批事实初始为 `PENDING`，记录待审批绝对截止时间，默认从创建起 15 分钟，可配置且保存本次实际值。
- **FR-006**：批准或拒绝 MUST 由经过认证且具有当前权限的人执行；批准人身份和角色 MUST 来自服务端认证上下文，不接受请求、卡片或 MCP `_meta` 自报。
- **FR-007**：批准 MUST 核对 Incident 未 `CLOSED`、Action 仍为待审批、未过期且绑定未变；成功后审批为 `APPROVED`、Action 为 `APPROVED`，记录批准人、批准时间和执行授权绝对截止时间，默认批准后 5 分钟，可配置且保存本次实际值。
- **FR-008**：拒绝 MUST 将审批记为 `REJECTED`、Action 记为 `APPROVAL_REJECTED` 并保存操作者和原因；过期 MUST 分别使用审批 `EXPIRED` 与 Action `EXPIRED`。上述结果均不得被迟到批准重新授权。
- **FR-009**：Action 状态合法转换 MUST 严格限定为 `PENDING_APPROVAL -> APPROVED | APPROVAL_REJECTED | EXPIRED`、`APPROVED -> DISPATCHING | EXPIRED`、`DISPATCHING -> EXECUTING | FAILED | EXECUTION_REJECTED | EXPIRED`、`EXECUTING -> SUCCEEDED | FAILED | EXECUTION_REJECTED | UNKNOWN`、`UNKNOWN -> SUCCEEDED | FAILED`；其他转换 MUST 拒绝。确定终态不可再次执行，`UNKNOWN` 不可回到 `EXECUTING`。
- **FR-010**：审批状态 MUST 仅允许 `PENDING -> APPROVED | REJECTED | EXPIRED`；票据状态 MUST 仅允许 `ISSUED -> CONSUMED | EXPIRED`。并发决定、派发、消费、清扫、回执和对账 MUST 校验预期状态及版本，至多一个互斥结果生效。
- **FR-011**：Agent 确认卡 MUST 只引用 `actionId` 并展示 Incident 权威审批状态；消息 ID、卡片状态或自然语言回答本身 MUST NOT 作为执行授权。
- **FR-012**：Incident MUST 独立负责有效 `APPROVED` Action 的异步调度、过期清扫和故障恢复；Agent 恢复 MUST 只查询 Action，不能重新调用原写工具。执行端不可用不得阻断告警、Incident 查询或人工生命周期操作。
- **FR-013**：首次有效调度 MUST 核对 Incident 未 `CLOSED`，为 Action 建立至多一个逻辑 Execution、固定执行幂等键并签发一次性不透明票据；Action 在授权窗口内进入 `DISPATCHING`。网络调用 MUST 在调度事实提交后才可能发生。
- **FR-014**：票据 MUST 使用不可预测秘密，持久化事实只保存秘密摘要而非明文；每个 Execution 同时最多一个 `ISSUED` 票据。默认票据有效期 2 分钟，可配置且不得晚于批准授权截止时间。
- **FR-015**：票据消费前 MUST 对调用服务身份、Action、Incident 当前未 `CLOSED`、审批与授权有效期、Execution、工具与版本、目标、原始参数的规范摘要、幂等键和票据状态做完整绑定校验；仅首次合法消费授予执行许可并将 Action 置为 `EXECUTING`。
- **FR-016**：主应用到 `mcp-server` 与反向票据消费/回执提交 MUST 使用彼此独立、可轮换的服务身份凭据；凭据和票据明文不得进入仓库、日志、响应或验收证据。跨主机通信 MUST 使用加密传输；开发环境只允许本机回环例外。`_meta` 仅作关联信封，不能单独充当身份或审批。
- **FR-017**：受保护模拟工具在所有入口 MUST 统一强制服务身份与在线票据消费；无票、重放、失效或绑定不一致必须在副作用前失败关闭。未认证请求不能通过自报 `actionId` 使 Action 进入拒绝或其他终态。
- **FR-018**：同一票据重复消费 MUST 返回结构化 `DUPLICATE` 或已知当前结果，不能再次启动工具；同一 Action 不得产生第二个逻辑 Execution。
- **FR-019**：演示工具 MUST 仅修改隔离的模拟状态，提供确定的目标解析、执行幂等控制、只读对账、超时结果评估和结构化回执；不得访问真实基础设施处置入口。
- **FR-020**：工具准入 MUST 声明版本化的 `maxExecutionDuration` 与 `receiptGracePeriod`；P0 默认分别为 2 分钟与 3 分钟，可配置且每次 Execution 保存实际值。工具实际强制超时不得大于声明的最大执行时长。
- **FR-021**：合法票据消费时 MUST 记录可信 `executionStartedAt`，并固定 `receiptDueAt = executionStartedAt + maxExecutionDuration + receiptGracePeriod`；票据到期仅限制执行启动，不能充当执行超时或回执截止。
- **FR-022**：工具结果 MUST 以版本化结构化回执表达 `SUCCESS`、`FAILED`、`REJECTED`、`DUPLICATE` 或 `UNKNOWN`，并含 Action、Execution、执行幂等键、请求、工具、模拟资源、结果码、可信发生时间和安全摘要；自然语言文本或单一 `isError` 不得决定副作用结果。
- **FR-023**：`mcp-server` 完成工具调用后 MUST 先向 Incident 幂等提交同一回执，再返回工具响应；主应用取得响应后 MUST 通过第二路径幂等提交。相同回执只生效一次，冲突确定终态不得覆盖，必须告警并进入人工核查。
- **FR-024**：已认证且绑定完整的执行前工具或策略拒绝 MUST 记 `EXECUTION_REJECTED` 与安全原因码；`DISPATCHING` 时只有合法调度上下文或 Incident 自身确认的绑定拒绝可触发该状态，`EXECUTING` 时仅副作用发生前的工具侧拒绝可触发。自然到期使用 `EXPIRED`，不混同拒绝。
- **FR-025**：`DISPATCHING -> FAILED` 仅能用于有证据确认未启动且没有仍可消费票据的确定故障；原因和证据引用 MUST 可审计。消费后故障不能沿此路径推定未执行。
- **FR-026**：消费前连接建立或暂时网络故障，只有仍能证实原票据为 `ISSUED`、仍在有效期且同一调度进程持有明文时，才 MAY 自动短退避重试，默认最多 3 次；票据已消费或状态不可查 MUST 停止自动派发。
- **FR-027**：Worker 崩溃而票据明文丢失时，恢复 MUST NOT 重建秘密；仅当 Incident 未 `CLOSED`、Action 仍 `DISPATCHING`、授权有效且无已消费票据时，先令旧票据失效，再为同一 Execution 与幂等键签发替代票据。迟到旧票据必须拒绝，但不得因其到达而错误终结持有有效替代票据的 Action。
- **FR-028**：按时间清扫 MUST 使用可信时间将过期待审批 Action/审批、过期 `APPROVED` Action 和过期 `ISSUED` 票据收敛；`DISPATCHING` 且无有效票据时，授权仍有效须交给恢复流程，只有授权也过期才由时间清扫转 `EXPIRED`。Incident 关闭触发的处置许可失效遵循 FR-038，不视为时间清扫。
- **FR-029**：工具超时后 MUST 先评估可验证证据；只有证明副作用未开始或已回滚，才可提交 `FAILED` 及 `TIMEOUT_PROVEN_ROLLED_BACK`；证据不足必须立即提交 `UNKNOWN` 及 `TIMEOUT_UNPROVEN`，不得自动再次执行。
- **FR-030**：`UNKNOWN` 回执提交失败时仅可有限重试提交同一回执，不可重调工具；仍失败时由绝对 `receiptDueAt` 清扫兜底。`EXECUTING` 超过该截止且没有确定终态回执 MUST 转 `UNKNOWN` 并发起只读对账。
- **FR-031**：`UNKNOWN` 仅可由完整绑定的已认证迟到回执、只读对账或有专门权限且提交原因与可核查证据的人工结论收敛为 `SUCCEEDED`/`FAILED`。无法判断保持 `UNKNOWN`；与确定终态冲突的结论不得覆盖，并须告警和人工核查。
- **FR-032**：只读对账 MUST 仅观察模拟目标和稳定执行身份，不得调用写工具或改变模拟目标；确认已应用为 `SUCCEEDED`，确认未应用或已回滚为 `FAILED`，不确定则保持 `UNKNOWN`。
- **FR-033**：Action、审批、Execution、票据状态、回执及人工结论 MUST 可凭稳定标识查询；人员查询和审批 MUST 执行权限检查，内部票据与回执接口 MUST 执行服务身份检查。未授权查询不得泄露秘密、敏感参数或其他 Incident 的 Action。
- **FR-034**：每次生效的提议、审批决定、调度、票据替换或消费、状态变化、回执、对账及人工收敛 MUST 在同一 Incident Timeline 中产生只追加事实，复用 Spec A 的 `incidentId`、Incident 内顺序、稳定事实身份、去重和内容安全约束；本功能的处置事实 MUST 有区别于 Spec A 五种告警与生命周期事件的明确类型，且不得改变其既有含义或历史事实。失败或重复请求不得伪造成功事实。
- **FR-035**：查询界面或响应 MUST 清晰区分 `APPROVAL_REJECTED`、`EXECUTION_REJECTED`、`EXPIRED`、`FAILED` 与 `UNKNOWN`，显示安全原因、截止时间及可执行的下一步，不将 `UNKNOWN` 表述为失败或可直接重试。
- **FR-036**：新增执行必须创建关联原 Action 的新 Action，重新审批并取得新的执行幂等键；原 Action 的结果和 Timeline 不得被改写。
- **FR-037**：验收 MUST 覆盖授权成功、拒绝、过期、权限不足、Incident 关闭与票据消费竞争、票据篡改与重放、跨入口旁路、旧写工具停用与新工具默认拒绝、模拟副作用至多一次、Worker 崩溃恢复、替代票据竞争、消费后故障、超时证明、双路径回执丢失、迟到回执、只读对账、人工证据收敛以及待发布事件失败恢复与重复投递，并保留可复现输入、预期状态和脱敏证据。
- **FR-038**：Incident 成功关闭与其尚未开始执行的 `PENDING_APPROVAL`、`APPROVED` 或 `DISPATCHING` Action 的许可失效 MUST 作为同一受保护业务决定：这些 Action 转为 `EXPIRED`；待审批事实随之转为 `EXPIRED`，已批准事实保留原批准记录，尚为 `ISSUED` 的票据失效。关闭与票据消费 MUST 互斥裁决；已进入 `EXECUTING` 或 `UNKNOWN` 的 Action MUST 保留回执、超时与证据收敛路径，不得因关闭被改写为未执行。
- **FR-039**：每次首次生效的审批决定及权威执行回执 MUST 与其 Action 状态及 Timeline 事实形成同一可恢复的业务提交，并产生稳定身份的待发布领域事件；重复投递或重复回执不得产生新的业务结论。事件发布失败不得回滚已确认的审批或执行事实，也不得阻断 Incident 的告警、查询和合法生命周期操作。本要求不把每条 Timeline 事实自动变成待发布事件；具体事件类型、负载和发布契约留待计划与 contracts 定义。
- **FR-040**：Spec B 对共享 Timeline 和领域事件的扩展 MUST 保留 Spec A 已确定的五种 Timeline 事件类型、稳定事实身份及两种领域事件的语义与去重规则；处置事实须能凭稳定 `actionId`、适用时的 `executionId` 与同一 `incidentId` 关联，且不得重写 Spec A 的历史记录。扩展所需的具体数据约束和迁移方式留待 plan/data-model。
- **FR-041**：MVP 的所有 MCP 入口 MUST 只允许经服务端核查的只读工具，或已纳入本规格 Incident 审批、幂等键与 Timeline 链路的单个模拟写工具。现有未纳入该链路的写工具 MUST 从可执行注册与工具发现中停用；已知名称直调、Agent 确认卡或其他入口均不得使其产生副作用。新增、未分类或只靠工具自报只读属性的注册 MUST 默认拒绝，不能自动恢复旧写工具。

### 关键实体（功能涉及数据时填写）

- **Incident**：Spec A 的事件实体；本功能只以 `incidentId` 关联处置，不更改告警聚合语义。
- **Action**：不可变的处置提议与当前生命周期，含 `actionId`、`incidentId`、来源去重身份、工具/目标/参数绑定、执行幂等键、状态版本与有效期。
- **Approval**：绑定 Action 内容的人工决定，含真实审批人、权限快照、决定、原因和绝对时间。
- **Execution**：一个 Action 唯一的逻辑执行，含稳定 `executionId`、开始时间、时长策略、`receiptDueAt` 和结果引用。
- **Ticket**：一次性执行许可，含身份、秘密摘要、有效期、状态及替换原因；秘密明文不持久化。
- **Receipt**：已认证且完整绑定的结构化执行结果，可由两条提交路径幂等抵达。
- **Timeline 事实**：附着于 Incident 的只追加处置审计事实，引用 `actionId`、`executionId` 和必要安全摘要。
- **领域事件**：审批决定或权威执行回执生效后，供下游可靠获知该业务事实的稳定待发布记录；不替代 Timeline。
- **模拟目标**：隔离的演示资源状态与只读对账依据，不代表真实运维资源。

## 成功标准（必填）

### 可度量结果

- **SC-001**：正常场景中，1 个有效 Action 对应 1 个审批事实、最多 1 个逻辑 Execution，模拟副作用启动次数为 1；重复提议和重复票据请求均不增加该次数。
- **SC-002**：无审批、无服务身份、无有效票据、绑定篡改和任意受保护入口旁路的验收样例，模拟目标变化次数均为 0。
- **SC-003**：待审批 15 分钟、批准授权 5 分钟和票据最多 2 分钟的默认边界可由受控时间场景逐项验证；配置覆盖时每条记录均能展示其实际绝对截止时间。
- **SC-004**：所有注入的消费后不确定故障均不触发第二次写工具调用；不能证明未执行的超时全部显示为 `UNKNOWN`，能证明未开始或回滚的超时全部保留证明并显示为 `FAILED`。
- **SC-005**：超过 `receiptDueAt` 且无确定回执的全部验收样例最终进入 `UNKNOWN`；迟到回执、只读对账和人工证据各至少有一个收敛为确定结果的可复现样例。
- **SC-006**：所有重复的相同终态回执得到原结论；所有相反的确定终态回执保留原结论并产生可观察核查信号，覆盖率为 100%。
- **SC-007**：Worker 恢复与消费竞态的全部验收样例中，同一 Execution 同时有效待消费票据数不超过 1，实际模拟副作用启动次数不超过 1。
- **SC-008**：从任何 Action 状态出发，授权用户均可根据稳定 `actionId` 查明当前状态、最近安全原因与下一步；Agent 会话恢复的全部样例均不重复执行写工具。
- **SC-009**：验收目录列出的每个成功及失败场景均有可复现步骤、预期结果、Timeline/回执核对项和脱敏证据；密钥与票据明文泄露项为 0。
- **SC-010**：安全演示工具的每次验收运行只改变隔离模拟目标；真实基础设施处置调用次数为 0。
- **SC-011**：Incident 关闭先于票据消费的全部验收样例中，新执行启动次数为 0，未消费票据不可再用；消费先于关闭的样例仍得到确定结果或 `UNKNOWN` 与证据收敛，且不发生第二次启动。
- **SC-012**：审批决定与权威回执在发布失败和重复投递场景中仍保有唯一的 Action 结论、Timeline 事实和稳定事件身份；Spec A 原有事件与事实的内容和身份不变。
- **SC-013**：MVP 中枚举所有 MCP 入口和已登记工具后，未纳入 Incident 审批链的旧写工具在发现结果中为 0；逐个以已知名称从各入口直调，副作用次数均为 0；未经核查的新工具注册被拒绝。

## 假设

- Spec A v1.0 已定义稳定的 Incident、Timeline 及授权用户上下文契约，但相关业务代码尚未实施；本功能不以 Agent 消息存储作为安全事实来源。
- Spec A 的数据模型当前仅列出五种 Timeline 类型和两种待发布领域事件；Spec B 在同一事实边界增加处置类型与发布契约，具体兼容扩展由后续 plan/data-model/contracts 说明，不能直接套用 Spec A 的封闭类型约束。
- 当前 Agent 确认路径和 MCP 工具入口尚未满足本规格安全协议；它们是后续计划的改造对象，并非既有可用保障。
- 本规格只开放一个专用安全演示写工具；旧入口只保留经服务端核查的只读工具。其确切工具名、请求字段、模拟资源形态、规范化规则和错误码由 plan/contracts 固化，不得改变本规格的审批、绑定、一次性消费与只读对账语义。
- 无实时推送要求；人员和 Agent 可通过状态查询观察执行进度。权限复用现有登录身份与服务端校验能力，不建设通用 IAM。
- 性能或可靠性结论仅依据实际运行的可复现证据报告，不因本规格目标而声称已经达成。

## 依赖与范围外

- **依赖**：Spec A v1.0 的 `incidentId`、Incident 状态和 Timeline；DEC-008 至 DEC-013、DEC-017 至 DEC-020 已批准的边界。计划提出的长期决策已归档；未来若再发现需固化新的持久数据或架构决策，先提交拟新增 ADR 内容及理由，获确认后才修改 `docs/DECISIONS.md`。
- **范围外**：Runbook/RAG 诊断及其持久化 TBD；真实服务器、Kubernetes、数据库或云资源处置；多租户、通用工作流、通用 IAM、插件平台；无关 UI、额外告警源、推测性基础设施；业务代码、数据库迁移与前端实现（这些属于未来实施，不属于本次规格交付）。
