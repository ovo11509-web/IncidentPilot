# IncidentPilot 项目宪章

## 核心原则

### 一、署名与贡献可追溯
本仓库必须保留 `nageoffer/ragent` 的 Git 历史、Apache-2.0 许可证、相关上游声明和源码许可头。文档、发布材料及简历描述必须区分上游能力与 IncidentPilot 新增贡献。不得通过改写历史掩盖代码来源。

### 二、由持久化边界保证事件正确性
告警幂等、Incident 聚合、合法状态转换、处置执行和时间线完整性必须在共享的持久化边界得到保证。业务幂等应尽可能由数据库约束兜底。Incident 时间线必须是只能追加的业务事实，不能用模型 Trace 或应用日志替代。

### 三、人工控制有副作用的操作
只读诊断工具可以无需审批执行。所有会产生副作用的 MCP 操作必须在服务端完成鉴权，经过人工明确批准，使用幂等键保护，并记录到 Incident 时间线中。MVP 只能操作安全的模拟资源；接入真实基础设施前必须另建 Spec 并完成安全评审。

### 四、按 Spec 控制交付范围
非平凡产品变更必须先经过仓库内 Spec Kit 工作流，再进入实现阶段。Spec 必须声明验收条件和明确的范围外事项。三周 MVP 优先完成一条端到端的“告警到处置”流程；推测性基础设施、额外适配器和无关 UI 必须延后，直到核心流程通过验证。

### 五、有证据后再做结论
行为变更必须具备能够覆盖它的最小有效自动化检查。持久化、并发和跨进程行为在适用时必须提供集成验证证据。性能、可靠性、评测和规模结论必须引用可复现的实际运行记录；估算值或模型生成的数字不得冒充实测结果。

## 技术与安全约束

- 支持基线为 Java 17、Spring Boot 4、Maven、PostgreSQL 以及现有 React 18/Vite 前端。增加包、服务或抽象前，必须先复用当前模块和依赖。
- 密钥不得进入受版本控制的源码、Spec、日志和文档。
- 告警载荷、用户输入、模型输出和 MCP 参数均不可信，必须在各自信任边界进行校验。
- MVP 不得修改真实服务器、Kubernetes、数据库或云资源。此类扩展需要明确授权并建立新的 Spec。
- 除非正式修订项目范围，否则全量包名或模块重命名、多 Agent 编排、服务网格、Nacos、Gateway、Seata 和生产 Kubernetes 均不属于 MVP。

## 开发流程与质量门禁

1. 未解决的产品或架构选择先使用 `$brainstorming`。
2. 使用 `$speckit-specify`、`$speckit-plan` 和 `$speckit-tasks` 管理需求、设计与实施顺序。
3. 产物需要一致性检查时，在实施前使用 `$speckit-analyze`；随后使用 `$speckit-implement` 执行已批准任务。
4. 先运行聚焦测试，再根据影响范围扩展到模块、集成、构建和 UI 检查，并如实记录缺失的前置条件。
5. 最终检查差异中是否包含无关修改、生成文件、密钥、许可证破坏或未完成迁移。
6. 提交、推送、合并、部署、付费供应商调用和远程写入都需要明确授权。

## 治理

本宪章约束 Spec Kit 产物和实现决策。按照 `AGENTS.md` 的权限顺序，当前用户指令和实时可执行契约拥有更高优先级。修改本宪章必须说明理由，并为受影响的 Spec 或代码提供迁移说明。版本遵循语义化规则：不兼容的治理变更提升主版本，新增或实质扩展原则提升次版本，文字澄清和非语义调整提升修订版本。每个 Spec 和评审都必须检查适用原则；无合理说明的违反项会阻止进入实施阶段。
