# 任务：[功能名称]

**输入**：`/specs/[###-feature-name]/` 中的设计文档

**前置条件**：plan.md（必需）、spec.md（用户故事必需）、research.md、data-model.md、contracts/

**测试**：下方示例包含测试任务。仅当功能规格明确要求测试时才保留测试任务。

**组织方式**：任务按用户故事分组，以便每个故事都能独立实现和测试。

## 格式：`[ID] [P?] [Story] 描述`

- **[P]**：可以并行执行（涉及不同文件且不存在依赖）
- **[Story]**：任务所属的用户故事（例如 US1、US2、US3）
- 描述中必须包含准确的文件路径

## 路径约定

- **单体项目**：仓库根目录下的 `src/`、`tests/`
- **Web 应用**：`backend/src/`、`frontend/src/`
- **移动应用**：`api/src/`、`ios/src/` 或 `android/src/`
- 下方路径默认采用单体项目结构，应根据 plan.md 中的结构调整

## 依赖关系与执行顺序

### 阶段依赖

- **准备（Phase 1）**：无依赖，可以立即开始
- **基础能力（Phase 2）**：依赖准备阶段完成，并阻塞所有用户故事
- **用户故事（Phase 3 及以后）**：全部依赖基础能力阶段完成
  - 基础能力完成后，各用户故事可以并行实施（人员允许时）
  - 也可以按照 P1、P2、P3 的优先级顺序实施
- **完善（最终阶段）**：依赖所有计划交付的用户故事完成

### 用户故事依赖

- **用户故事 1（P1）**：基础能力完成后即可开始，不依赖其他故事
- **用户故事 2（P2）**：基础能力完成后即可开始；可以与 US1 集成，但必须可独立测试
- **用户故事 3（P3）**：基础能力完成后即可开始；可以与 US1 或 US2 集成，但必须可独立测试

### 每个用户故事内部

- 如包含测试，MUST 先编写测试并确认其在实现前失败
- 先完成模型，再完成服务
- 先完成服务，再完成端点
- 先完成核心实现，再完成集成
- 完成当前故事后再进入下一优先级

### 并行机会

- 所有标记 `[P]` 的准备任务可以并行执行
- 所有标记 `[P]` 的基础任务可以在 Phase 2 内并行执行
- 基础能力完成后，不同用户故事可以由不同人员并行实施
- 同一用户故事中标记 `[P]` 的测试可以并行执行
- 同一故事中涉及不同文件的模型任务可以并行执行

## 实施策略

### MVP 优先（只实现用户故事 1）

1. 完成 Phase 1：准备
2. 完成 Phase 2：基础能力（阻塞所有故事）
3. 完成 Phase 3：用户故事 1
4. 停止并验证：独立测试用户故事 1
5. 就绪后部署或演示

### 增量交付

1. 完成准备和基础能力，形成可用基础
2. 增加用户故事 1，独立测试后部署或演示 MVP
3. 增加用户故事 2，独立测试后部署或演示
4. 增加用户故事 3，独立测试后部署或演示
5. 每个故事都在不破坏既有故事的前提下增加价值

### 并行团队策略

多人协作时：

1. 团队共同完成准备和基础能力
2. 基础能力完成后：
   - 开发者 A：用户故事 1
   - 开发者 B：用户故事 2
   - 开发者 C：用户故事 3
3. 各故事独立完成并集成

## 说明

- `[P]` 表示任务涉及不同文件且不存在依赖，可以并行执行
- `[Story]` 标签将任务映射到具体用户故事，确保可追踪性
- 每个用户故事都应能独立完成和测试
- 实现前确认对应测试失败
- 仅在用户明确授权提交时，按任务或逻辑任务组组织提交
- 可以在任一检查点停止并独立验证当前故事
- 避免含糊任务、同文件冲突，以及破坏故事独立性的跨故事依赖
