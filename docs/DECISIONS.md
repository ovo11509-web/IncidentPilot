## DEC-001：采用仓库内文档管理长期上下文

- 日期：2026-09-21
- 状态：已接受
- 替代关系：无

### 问题

项目方案分散在历史聊天中，后续任务难以获得稳定、可版本控制且可复核的上下文。

### 可选方案

1. 继续依赖历史聊天和 AI 记忆。
2. 使用一个大型说明文件保存全部内容。
3. 按上下文、架构、决策、任务和排错笔记拆分为仓库内文档。

### 最终方案

采用第三种方案。使用 `PROJECT_CONTEXT.md`、`ARCHITECTURE.md`、`DECISIONS.md`、
`TODO.md` 和 `NOTES.md` 分别保存不同类型的长期信息，由根目录 `AGENTS.md` 规定读取和更新规则。

### 选择原因

- 文档随代码版本化，不依赖单个聊天会话。
- 不同类型信息拥有明确归属，减少单个文档膨胀和互相覆盖。
- 可以清楚区分当前事实、已确认决策、待办事项和临时经验。

### 影响范围

- 根目录 `AGENTS.md`。
- `docs/` 下的项目级上下文文档。
- 后续所有设计、开发、排错和任务收尾流程。

## DEC-002：Spec Kit 是唯一的功能规格体系

- 日期：2026-09-21
- 状态：已接受
- 替代关系：无

### 问题

项目需要把长期项目上下文和单个功能的需求、计划及实施任务区分开，同时避免维护两套相互冲突的 Spec。

### 可选方案

1. 仅使用聊天或普通 Markdown 临时计划。
2. 使用 GitHub Spec Kit 管理功能规格。
3. 同时维护 Spec Kit 和另一套自定义规格目录。

### 最终方案

使用 `.specify/` 和 `.agents/skills/speckit-*` 作为唯一有效的功能规格体系。项目级文档提供长期
上下文和决策，不能替代具体功能的 Spec；也不创建第二套并行 Spec 格式。

### 选择原因

- 规格、计划、任务和实施之间有固定流转路径。
- 降低不同代理和不同会话之间的指令漂移。
- 项目级文档与功能级产物职责清晰。

### 影响范围

- `.specify/`、`.agents/skills/`。
- `AGENTS.md` 中的开发流程。
- 后续所有非平凡功能开发。

## DEC-004：核心质量优先于固定工期

- 日期：2026-09-21
- 状态：已接受
- 替代关系：替代“以三周约 42 小时作为硬性交付边界”的早期规划假设

### 问题

固定工期会迫使项目在幂等、安全、审计、异常恢复和测试之间进行不合理取舍。

### 可选方案

1. 以固定工时为硬约束，到期即压缩功能或质量。
2. 完全取消范围控制，持续扩张为通用平台。
3. 以质量门驱动阶段交付，保留明确范围，工时只用于估算和排序。

### 最终方案

采用第三种方案。优先把一条告警到处置链路做正确、做完整，再根据已确认需求扩展；不能用赶工
作为省略核心工程质量的理由，也不为未经验证的未来需求预建平台能力。

### 选择原因

- 项目的核心价值来自可信的事件链路，而不是功能数量。
- 质量门能够同时避免赶工债务和无边界过度设计。
- 更适合持续学习、演进和长期维护。

### 影响范围

- 里程碑、验收标准和任务优先级。
- 数据一致性、安全控制、测试与文档要求。
- 原“三周 42 小时”仅保留为历史估算，不再作为验收条件。

## DEC-005：有副作用的 MCP 处置采用强制安全边界

- 日期：2026-09-21
- 状态：已接受
- 替代关系：无

### 问题

Agent 生成的工具参数和调用意图不能被视为可信输入，直接执行写操作可能导致重复或越权处置。

### 可选方案

1. Agent 决定后直接调用写工具。
2. 仅由前端显示确认框，后端不强制校验。
3. 服务端强制人工审批，执行请求携带幂等键，审计全过程，并限制为演示或模拟资源。

### 最终方案

采用第三种方案。在后续决策明确真实执行协议前，不允许 IncidentPilot 对真实服务器、集群、数据库
或云资源执行变更。

### 选择原因

- 前端确认不能形成可靠的安全边界。
- 幂等键和审计记录能够降低重试、重复提交和事后无法追溯的风险。
- 模拟资源足以验证工作流，同时避免在方案尚未成熟时引入真实破坏面。

### 影响范围

- Agent 人工确认流程。
- Incident Action 数据模型。
- MCP 服务、工具参数和执行协议。
- 前端确认交互、审计和测试。

### 影响范围

- 测试、评测、演示、README 和简历材料。

## DEC-007：选择三项高价值增强能力

- 日期：2026-09-21
- 状态：已接受
- 替代关系：无

### 问题

核心告警到处置流程之外，还需要选择少量能够提高项目技术深度和简历辨识度的能力，且不能让
范围扩张为多租户、多 Agent 或通用插件平台。

### 可选方案

1. 以工程深度为主：可靠性实验、RAG 评测和 MCP 安全。
2. 以功能数量为主：增加多个告警源、执行器和管理页面。
3. 以平台广度为主：增加多租户、多 Agent、Kubernetes 和插件体系。

### 最终方案

采用第一种方案，选择以下三项：

1. 告警可靠性与故障回放实验室。
2. Runbook RAG 评测门禁。
3. MCP 安全处置网关。

指标、日志、Trace 和统一关联标识作为三项能力共同的验证基础，不单独扩张为第四个平台项目。

### 选择原因

- 三项能力分别证明分布式后端正确性、AI 工程质量和 Agent 操作安全，互补性强。
- 每项都能形成代码、测试、故障演示和可复现报告，而不只是技术名词。
- 能够共用同一条 Incident 主流程，避免形成三个互不相关的子项目。

### 影响范围

- 告警处理、消息可靠性和故障测试。
- Runbook 数据、诊断输出、评测集和 CI 门禁。
- Agent 审批、Incident Action、MCP 调用协议和安全测试。
- 全链路 Trace、指标、演示脚本和项目说明。

## DEC-008：Incident 领域归属于主应用独立模块

- 日期：2026-09-21
- 状态：已接受
- 替代关系：无

### 问题

需要确定告警、Incident、Action 和时间线由哪个模块拥有，并保证模型、RAG、消息队列或 MCP
暂时不可用时，事件响应的核心记录和人工操作仍然可用。

### 可选方案

1. 在 9090 主应用中新建独立 `incident` Maven 模块。
2. 由独立 `mcp-server` 持有 Incident 领域和主数据。
3. 将 Incident 代码放入现有 `rag` 或 `system` 模块。

### 最终方案

采用第一种方案：

- `incident` 依赖 `framework` 和 `system`。
- `agent` 增加对 `incident` 的依赖，读取 Incident 快照并参与诊断和处置编排。
- `bootstrap` 装配 `incident`、`rag` 和 `agent`。
- `mcp-server` 保持独立内部执行器，不拥有或直接决定 Incident 主状态。
- `incident` 负责告警、Incident、Action 审批记录和只追加时间线，不负责 RAG、Agent 推理、
  MCP 工具实现或前端页面。

物理数据库、消息一致性和 MCP 跨进程执行协议由后续独立决策确定。

### 选择原因

- 复用主应用现有认证、用户上下文、审计和事务基础设施。
- AI 和 MCP 故障不会阻断告警接入、事件查询、人工状态流转和时间线记录。
- 独立业务模块可以保持清晰职责，同时避免过早拆分微服务和引入分布式事务。
- 当前 `mcp-server` 的本机演示定位和可重建数据库不适合作为 Incident 主数据边界。

### 影响范围

- 根 Maven 模块和 `bootstrap`、`agent` 的依赖关系。
- Incident Controller、应用服务、领域模型和持久化实现。
- Agent 读取 Incident 和记录处置过程的调用方式。
- MCP 服务边界、前端 API 入口和未来服务拆分条件。

## DEC-009：Incident 初期共享主数据库并保持可拆分边界

- 日期：2026-09-21
- 状态：已接受
- 替代关系：无

### 问题

需要确定 Incident 主数据初期存放位置和迁移方式，同时避免为了未来可能发生的物理拆库，
现在就承担独立数据库、多数据源和分布式事务的复杂度。

### 可选方案

1. Incident 从第一天开始使用独立 PostgreSQL 和独立服务。
2. Incident 使用主数据库 `ragent`，通过严格领域所有权保持逻辑隔离。
3. Incident 使用 `mcp-server` 的可重建演示数据库 `ragent_bit`。

### 最终方案

采用第二种方案：

- Incident 表位于主 PostgreSQL `ragent`。
- 数据库变更使用 `resources/database/upgrades/` 的现有增量 SQL 机制。
- `incident` 独占自身表、Mapper 和持久化事务，其他模块通过应用服务访问。
- Incident 内部允许外键和本地事务；跨领域只保存稳定 ID 和必要快照，不建立外键或 SQL JOIN。
- 跨领域一致性通过服务接口或后续确定的可靠事件机制处理，不使用共享本地事务。
- 初期不增加独立 Schema、多数据源、CDC 或零停机迁移设施。
- 出现独立部署、扩缩容、故障隔离或团队所有权需求后，再评估物理拆库。

### 选择原因

- 与当前模块化单体和数据库升级方式一致，实现和本地开发成本最低。
- 可以复用主应用事务、连接池和备份流程。
- 逻辑边界清晰时，后期可以按 Incident 表集合迁移，而无需重写领域模型。
- 避免把尚未出现的拆库需求提前转化为多数据源和分布式一致性负担。

### 影响范围

- Incident 表结构、Mapper、事务和升级脚本。
- `agent`、`rag`、`system` 与 Incident 的调用方式。
- 报表查询、审计快照和跨领域数据引用。
- 未来拆库、数据迁移和服务拆分策略。

### 会显著增加拆库成本的操作

- 其他模块直接访问 Incident Mapper、DO 或表。
- 跨领域 SQL JOIN、数据库外键、触发器、视图或存储过程。
- 一个本地事务同时修改 Incident 与用户、Agent、RAG 等其他领域数据。
- 依赖主库共享序列、临时表或隐式 Schema 行为。
- 将 Incident 主数据写入 `ragent_bit`，或由 MCP 服务直接决定 Incident 主状态。
- 缺少迁移契约、校验方案的复制、缓存或双写。

## DEC-010：告警可靠接入采用数据库工作队列与 Transactional Outbox

- 日期：2026-09-22
- 状态：已接受
- 替代关系：无

### 问题

告警接入需要在重复、并发、乱序、应用崩溃、RocketMQ 不可用和消费失败时仍然可恢复，同时不能
让外部请求等待完整 Incident 聚合，也不能为了尚未出现的拆库需求引入分布式事务。需要确定告警
持久化、异步聚合、RocketMQ、Outbox/Inbox、重试和失败恢复的责任边界。

### 可选方案

1. 在告警 HTTP 请求中同步完成 Incident 创建或聚合后再返回。
2. 使用 RocketMQ 普通或事务消息作为告警持久化与聚合的必要入口。
3. 先在 PostgreSQL 可靠持久化 Alert 并返回 202，由数据库 Worker 聚合 Incident；提交后通过
   Transactional Outbox 向 RocketMQ 发布跨领域事件。

### 最终方案

采用第三种方案：

- 告警请求通过认证和输入校验后，在 Incident 本地事务中写入 Alert；只有事务提交成功才返回
  HTTP 202。202 表示告警已持久化且可恢复，不表示 Incident 已经创建。
- Alert 记录自身作为持久工作项，初期不增加独立通用 Inbox 或 Job 表。数据库 Worker 使用
  `FOR UPDATE SKIP LOCKED` 领取到期 Alert，每条 Alert 在一个短事务内完成创建或聚合 Incident、
  关联、Timeline 追加、Alert 状态更新和 Outbox 写入。
- 接入幂等由 `source_key + external_alert_id` 数据库唯一约束兜底。相同外部 ID 但载荷摘要不同
  视为冲突，不覆盖已接收数据。活动 Incident 由后续确认的聚合键和部分唯一索引仲裁并发创建；
  Timeline 与 Outbox 使用稳定业务事件键防止重复结果。
- Alert 处理状态为 `RECEIVED`、`PROCESSED`、`FAILED`。首次失败后默认自动重试五次，建议退避
  间隔为 10 秒、30 秒、2 分钟、10 分钟和 30 分钟并附加随机抖动；耗尽后由受权用户填写原因
  人工重放。初期不建立逐次 Attempt 历史表。
- Outbox 状态为 `PENDING`、`PUBLISHED`。Relay 使用普通同步消息并明确检查 `SEND_OK`；失败时
  持续指数退避，最长间隔 15 分钟，不自动丢弃事件。发送成功但发布状态提交失败时允许重复投递。
  已发布记录默认保留 7 天后分批清理，业务审计以 Timeline 为准。
- 初期使用单一 Incident 领域事件 Topic，消息包含稳定 `eventId`、`schemaVersion`、
  `incidentId`、`aggregateVersion` 和 `correlationId`，不依赖消息包装器随机 UUID 或 Broker 全局
  顺序。第一批事件为 `incident.created` 和 `incident.alert-attached`。
- `incident` 不预建通用 Inbox。产生持久化副作用的下游消费者在自己的本地事务中，以
  `consumer_name + event_id` 唯一约束或等价机制防重；DLQ 重放必须保留原 `eventId`。
- 告警接入和 Incident 聚合不依赖 RocketMQ、Redis 或进程内状态。RocketMQ 故障只积压 Outbox，
  不阻止可靠接入和 Incident 创建。当前本地单 Broker、异步刷盘配置仅用于开发和故障实验，不能
  作为生产高可用证据。
- 告警 Webhook 使用来源 ID、请求时间戳和 HMAC-SHA256 进行独立机器认证，不依赖 Sa-Token，
  并返回真实 HTTP 状态：新接收或仍在处理返回 202，已处理或已失败的幂等重复返回 200，同一
  外部 ID 对应不同载荷摘要返回 409，提交前的暂时数据库故障返回 503。请求字段和签名规范的
  完整契约在告警接入 Spec 中确认。

核心数据表初期为 `t_incident_alert`、`t_incident`、`t_incident_timeline` 和
`t_incident_outbox`。它们由 `incident` 模块独占，随 Incident 表集合一起保持未来物理拆分边界；
时间字段统一使用 `TIMESTAMPTZ`，核心记录不提供普通业务删除能力。告警指纹字段、聚合窗口、
`aggregation_key` 计算规则和完整 Incident 状态机在后续 Spec 或独立决策中确认。

### 选择原因

- PostgreSQL 提交构成清晰的 202 可靠性边界，应用或消息队列故障不会让已接受告警丢失。
- 聚合只依赖 Incident 本地事务、行锁和数据库唯一约束，能够用真实 PostgreSQL 集成测试证明。
- RocketMQ 退出核心正确性路径，符合其不可用时仍能接入告警和创建 Incident 的既定模块要求。
- Outbox 提供跨领域至少一次发布，消费者按实际副作用按需增加 Inbox，避免预建通用消息平台。
- 所有核心表和恢复状态都归属 Incident 领域，未来可以整体迁移到独立数据库。

### 影响范围

- 告警 Webhook、查询和人工重放接口。
- Incident Alert、主表、Timeline、Outbox Schema 及其数据库约束。
- 数据库 Worker、Outbox Relay、RocketMQ Topic 和领域事件契约。
- 下游消费者的幂等边界、重试、DLQ 和重放约定。
- 告警可靠性故障实验、指标、日志、Trace 和集成测试。

## DEC-011：MCP 副作用执行采用 Incident 审批事实与一次性票据

- 日期：2026-09-22
- 状态：已接受
- 替代关系：无

### 问题

现有 Agent 写工具确认流程能够持久化确认卡并恢复 Agent 状态，但确认结果保存在可变的消息 JSON
和 Agent 运行状态中，没有独立审批记录、批准人权限、有效期、参数摘要、一次性执行授权或持久化
执行回执。主应用调用 MCP 时也没有服务身份认证，`_meta` 由调用方提供，不能单独证明调用身份；
网络超时还会被折叠为普通工具失败，无法区分“明确未执行”和“可能已经执行”。

需要在不建设通用授权平台或工作流引擎的前提下，确定 Incident Action、Agent 确认、主应用和
`mcp-server` 之间的审批、幂等、防篡改、防重放和未知结果恢复协议。

### 可选方案

1. 扩展 Agent 消息中的确认块，让聊天消息同时承担审批、执行票据和回执事实。
2. 由 Incident 模块持有 Action、审批、票据和执行回执，Agent 只作为交互适配器，
   `mcp-server` 只验证授权并执行。
3. 由 `mcp-server` 持有审批工作流和执行账本，主应用只展示状态。

### 最终方案

采用第二种方案，并遵循以下边界和协议：

- `incident` 是副作用操作的唯一安全事实来源。`IncidentAction` 保存不可变的 Incident、工具、
  工具版本、目标资源、规范化参数、参数摘要和执行幂等键；审批、票据、执行回执和 Timeline
  都属于 Incident 数据边界。
- Agent 确认卡只负责展示、收集决定和恢复交互。卡片必须引用 `actionId`，不得仅凭
  `messageId`、确认块状态或 Agent ToolUseBlock 授权 MCP 写操作。现有确认接口可以作为薄适配器，
  但权威决定必须由 Incident 应用服务完成。
- 审批记录绑定 Action、Incident、工具、目标资源、版本化规范参数摘要、执行幂等键、批准人、
  批准时间和授权有效期。批准人从当前登录会话和服务端权限判断取得，不接受请求体或 `_meta`
  指定。参数或目标变化时创建新 Action 并重新审批。
- Action 状态为 `PENDING_APPROVAL`、`APPROVED`、`APPROVAL_REJECTED`、`DISPATCHING`、
  `EXECUTING`、`SUCCEEDED`、`FAILED`、`EXECUTION_REJECTED`、`EXPIRED`、`UNKNOWN`。
  状态更新必须校验预期状态和版本；终态不能重新进入执行。`UNKNOWN` 只能通过经过服务认证且
  完整绑定的迟到结构化回执、只读对账或带证据的人工结论收敛为 `SUCCEEDED` 或 `FAILED`；再次
  执行必须创建新 Action 并重新审批。冲突终态不得覆盖，必须告警并进入人工核查。
- 审批状态为 `PENDING`、`APPROVED`、`REJECTED`、`EXPIRED`；票据状态为 `ISSUED`、
  `CONSUMED`、`EXPIRED`。每个 Action 只有一个逻辑执行和稳定的执行幂等键。
- 执行 Worker 在批准有效期内将 Action 转为 `DISPATCHING`，创建逻辑执行并签发 256 位随机的
  一次性不透明票据。数据库只保存票据秘密的 SHA-256 摘要，不保存或记录明文。
- `mcp-server` 在调用具体写工具前，必须使用独立服务身份向 Incident 内部接口在线消费票据。
  Incident 在一个事务中校验票据、审批、Action 状态、工具、目标、参数摘要和幂等键，并将票据
  原子更新为 `CONSUMED`、Action 更新为 `EXECUTING`。重复消费只返回 `DUPLICATE`，不再次调用工具。
- 主应用与 `mcp-server` 使用两个方向各自独立的高熵服务凭证；凭证由环境或秘密管理设施注入，
  支持轮换，不写入仓库和日志。开发环境允许 loopback；跨主机通信必须使用 TLS。P0 不建设
  OAuth Server 或通用 IAM，未来可替换为 mTLS 而不改变票据协议。
- `_meta` 只作为经过服务认证的传输信封，携带 Action、Execution、request、幂等键和票据引用；
  它本身不是身份认证、审批或授权凭据。
- MCP 结果使用结构化回执，结果语义为 `SUCCESS`、`FAILED`、`REJECTED`、`DUPLICATE`、
  `UNKNOWN`，不得从自然语言或单一 `isError` 推断副作用结果。`mcp-server` 完成工具调用后先回调
  Incident 幂等保存回执，再返回 MCP 响应；主应用收到响应后再次幂等写入同一回执。
- 只有数据库能够证明票据仍为 `ISSUED` 时，连接建立失败等消费前瞬态错误才允许在票据有效期内
  有限自动重试。票据一旦消费，网络超时、连接中断、进程崩溃、回执关联失败或无法查询票据状态
  都进入 `UNKNOWN`，禁止自动重放副作用。
- 每个获准的写工具必须提供确定的目标解析和只读对账能力。对账确认副作用存在时收敛为
  `SUCCEEDED`，确认未发生或已回滚时收敛为 `FAILED`；无法判断时保持 `UNKNOWN` 并要求有权限的
  人工处理。人工结论必须记录原因、证据和 Timeline。
- Incident 内部以外键、本地事务、唯一约束、条件更新和只追加 Timeline 保证关联；对 Agent、
  用户和 MCP 只保存稳定 ID 与必要快照，不建立跨领域外键或 SQL JOIN。`mcp-server` 不直接访问
  Incident 表，也不把审批、回执或 Timeline 写入可重建的 `ragent_bit`。
- P0 只接入一条安全的演示或模拟处置垂直链路。未满足审批绑定、票据校验、结构化回执和对账
  要求的现有写工具不得加入 Incident Agent 的可执行白名单。

### 选择原因

- 审批、执行和审计事实归属于同一个 Incident 聚合边界，Agent 消息删除或运行状态损坏不会改变
  安全结论。
- 在线消费不透明票据可以在不复制 Incident 数据、不共享数据库和不维护自包含令牌密钥体系的
  情况下实现一次性授权和参数绑定。
- “消费后不自动重试”明确选择 at-most-once 执行启动和可审计的 `UNKNOWN`，避免以可用性为由
  重复产生副作用。
- 双路径幂等回执能够覆盖普通响应丢失；无法跨资源原子提交的剩余窗口通过对账而不是盲目重试处理。
- 服务凭证、数据库约束和小型工具适配契约满足当前安全范围，同时避免建设未经需求验证的通用平台。

### 影响范围

- Incident Action、Approval、Execution、Ticket、Timeline 和 Outbox Schema。
- Agent 确认卡、确认接口、等待/恢复流程和 MCP 写工具桥接。
- 主应用 MCP Client、`mcp-server` 请求入口、服务身份认证和结构化回执。
- 数据库执行 Worker、票据消费与回执内部接口、UNKNOWN 对账和人工恢复接口。
- 日志、指标、告警、PostgreSQL 约束测试、接口安全测试、故障注入和端到端黄金路径。

DEC-011 是 DEC-005 服务端强制审批要求的实现细化；调度归属、超时收敛、全路径票据强制和
Agent 生命周期由 DEC-012 进一步明确。

## DEC-012：MCP 调度、超时收敛与全路径票据强制

- 日期：2026-09-22
- 状态：已接受
- 替代关系：无

### 问题

DEC-011 已确定 Incident 持有审批事实、一次性票据和执行回执，但尚未明确数据库调度 Worker 的
模块归属、时间驱动状态的执行者、`DISPATCHING` 阶段拒绝、受保护工具的旁路防护、迟到回执以及
Agent 会话如何跟随 Action 生命周期。若把这些问题留到实现阶段，可能形成模块循环依赖、永久
停留在 `EXECUTING` 的 Action，或允许旧 Agent 确认路径绕过票据校验。

### 可选方案

1. 由 `incident` 持有调度与过期清扫，定义出站端口，`agent` 实现 MCP 调度适配器，
   `bootstrap` 只负责装配。
2. 把调度 Worker 放入 `agent`，由 Agent 模块控制授权窗口和执行时序。
3. 把调度 Worker 放入 `bootstrap`，直接协调 Incident 与 MCP Client。

### 最终方案

采用第一种方案，并补充以下协议：

- `incident` 拥有 Action 调度 Worker、过期清扫 Worker 和 `RemediationDispatcher` 出站端口。
  `agent` 依赖 `incident` 并实现 MCP 调度适配器，可复用现有 MCP SDK 与连接配置，但必须保留
  消费前失败、消费后不确定和结构化回执语义，不得把传输异常折叠为普通 `isError`。`bootstrap`
  只装配实现，不承载业务 Worker。适配器或 `mcp-server` 不可用时，Incident 的告警、查询、人工
  状态流转和 Timeline 仍可启动和使用；处置调度失败关闭并按授权窗口收敛。
- 调度 Worker 使用 `FOR UPDATE SKIP LOCKED` 和条件更新在短事务内领取有效的 `APPROVED` Action，
  创建逻辑 Execution、签发票据并提交 `DISPATCHING`；事务提交后才调用出站端口，不在数据库事务
  或行锁内等待网络。同一进程内的消费前瞬态失败只有在数据库仍能证明票据为 `ISSUED` 时，才可
  使用内存中的明文票据有限重试；票据已消费或状态无法确认时禁止重放副作用。
- Worker 崩溃会丢失不落库的票据明文。恢复 Worker 不得重建或猜测原秘密；只要 Action 仍为
  `DISPATCHING`、授权窗口有效且没有已消费 Ticket，就可以在一个事务中处理恢复：原 Ticket 仍为
  `ISSUED` 时先条件更新为 `EXPIRED`，原 Ticket 已自然过期且当前没有 `ISSUED` Ticket 时直接继续，
  然后为同一逻辑 Execution 和幂等键签发替代 Ticket。数据库保证每个 Execution 同时最多一个
  `ISSUED` Ticket。若原 Ticket 已先被消费，恢复条件必须失败，不得签发或派发新票据，而应按
  `EXECUTING` 路径等待回执或超时收敛。被替代 Ticket 保存结构化失效原因；携带旧 Ticket 的迟到
  请求必须失败关闭，但在已存在当前 `ISSUED` 替代 Ticket 时不得把 Action 改为终态。
- 过期清扫 Worker 使用同一数据库工作队列模式和数据库 `CURRENT_TIMESTAMP` 执行条件更新：将
  超过待审批有效期的 Action 与 Approval 转为 `EXPIRED`，将超过授权窗口的 `APPROVED` Action
  转为 `EXPIRED`，并将超过有效期的 `ISSUED` Ticket 转为 `EXPIRED`。仍处于 `DISPATCHING` 且
  当前没有 `ISSUED` Ticket 的 Action，只有在授权窗口也已过期时才能转为 `EXPIRED`；授权窗口仍
  有效时必须留给恢复 Worker 补发替代 Ticket。每次有效转换都追加 Timeline；并发审批、消费、
  恢复、回执或清扫只能有一个条件更新成功。
- 票据有效期只约束何时允许开始执行，不作为执行超时。Incident 在票据消费事务中使用数据库时间
  写入 `executionStartedAt`，并持久化绝对的
  `receiptDueAt = executionStartedAt + maxExecutionDuration + receiptGracePeriod`。P0 演示工具的
  默认最大执行时长为 2 分钟、回执宽限期为 3 分钟，均可配置且每次 Execution 保存实际值。
  清扫 Worker 将超过 `receiptDueAt`、仍为 `EXECUTING` 且没有终态回执的 Action 条件更新为
  `UNKNOWN`，追加 Timeline 并触发后续对账，不自动再次执行工具。
- 每个 Incident 处置白名单工具必须在注册时声明并实现版本化准入契约，包括确定的目标解析器、
  只读对账器、`maxExecutionDuration`、`receiptGracePeriod` 和超时结果评估能力；这些值不是只适用
  所有工具的无差别全局常量，每次 Execution 保存本次实际采用值。`mcp-server` 对具体工具调用的
  强制超时不得大于该工具声明的 `maxExecutionDuration`。
- 工具调用超时后，适配器必须评估结果，禁止把超时乐观地统一映射为 `FAILED`。只有能够明确证明
  副作用尚未开始或已经回滚时，才提交 `FAILED` 和结构化原因码，例如
  `TIMEOUT_PROVEN_ROLLED_BACK`；无法证明是默认情形，必须立即提交 `UNKNOWN` 和原因码
  `TIMEOUT_UNPROVEN`。P0 单本地事务演示工具也只有在实际获得事务已中止回滚的可验证证据后，
  才能使用可证明的 `FAILED` 路径，不能仅凭事务注解推定。
- `UNKNOWN` 回执提交失败时，`mcp-server` 使用短退避有限重试同一幂等回执，重试不得再次调用
  工具；仍失败则由 `receiptDueAt` 清扫兜底。快速 `UNKNOWN` 会立即触发对账，但不是最终结论；
  工具线程后续得到确定结果时可以追加经过认证和完整绑定的迟到回执，使
  `UNKNOWN -> SUCCEEDED | FAILED`，只读对账也可完成同样收敛。与已有确定终态冲突时仍不得覆盖。
- Action 增加 `DISPATCHING -> EXECUTION_REJECTED` 合法转换，用于已认证的合法调度上下文或
  Incident 自身在票据消费事务中确认的工具、目标、参数摘要、幂等键或策略绑定拒绝；未认证请求
  不能依赖调用方提供的 `actionId` 改变 Action。拒绝保存结构化原因码，Action 进入终态后对应
  `ISSUED` Ticket 不再具备消费条件并由清扫 Worker 过期。
- `EXECUTING -> EXECUTION_REJECTED` 继续表示票据已消费后、产生副作用前的工具侧策略或业务拒绝；
  票据、审批或授权窗口自然过期仍使用 `EXPIRED`，不混入拒绝状态。
- 一旦写工具被列入 Incident 处置白名单，`mcp-server` 必须在所有调用路径统一执行服务身份认证和
  票据在线消费。旧 Agent 确认卡、直接 MCP 调用或其他客户端都不能形成旁路；无票据、无效票据、
  重放票据或绑定不一致必须在副作用发生前失败关闭。P0 优先接入一个专用安全演示工具，不要求
  立即迁移所有现有写工具。
- `UNKNOWN` 只能依据经过服务认证且绑定完整的迟到结构化回执、只读对账或带权限、原因和证据的
  人工结论收敛。与已有终态一致的回执幂等返回原结果；迟到回执、对账或人工结论与已有终态冲突
  时不得覆盖，必须告警并进入人工核查。
- Agent 确认卡只引用 `actionId` 并展示 Incident 权威状态。会话恢复时按 `actionId` 查询 Action；
  发现拒绝、过期或其他终态时结束等待。批准后由数据库 Worker 独立调度执行，Agent 恢复流程不得
  再调用原写工具；非终态只展示当前进度。P0 不要求增加推送机制。

### 选择原因

- Incident 在不反向依赖 `agent` 的前提下控制授权窗口、数据库状态和恢复时序，符合既定模块方向。
- 出站端口隔离业务调度与 MCP 传输，`bootstrap` 保持为薄装配层。
- 数据库时钟、条件更新和持久化执行截止时间让所有时间状态在多实例与崩溃恢复后仍可收敛。
- 执行端全路径票据强制消除旧确认流程和直接 MCP 调用的授权旁路。
- 迟到回执与 Agent 恢复规则补齐了 UNKNOWN 和会话等待的可达收敛路径。

### 影响范围

- `incident` 调度端口、Action 调度 Worker、过期清扫 Worker 和数据库领取查询。
- `agent` MCP 调度适配器、确认卡和会话等待/恢复流程。
- Action、Execution、Ticket 时间字段、状态转换、拒绝原因码和 Timeline 事件。
- `mcp-server` 受保护工具入口、服务身份认证、全路径票据消费和旁路测试。
- 超时结果评估、迟到回执、并发清扫、消费后崩溃、双路径回执丢失和 UNKNOWN 对账测试。

## DEC-013：告警 Webhook 限制签名时效、载荷和幂等响应

- 日期：2026-09-22
- 状态：已接受
- 替代关系：无

### 问题

DEC-010 已确定来源 ID、请求时间戳和 HMAC-SHA256 机器认证，但没有限定签名时间窗口、请求体
大小和 JSON 结构复杂度，也没有要求已失败告警的幂等重复响应暴露实际处理状态。攻击者或错误
客户端可能重放旧签名、提交畸形大载荷，或把 HTTP 200 误解为告警已经成功形成 Incident。

### 可选方案

1. 仅依靠告警业务唯一约束处理重放，并把签名和输入限制全部留给实现默认值。
2. 在告警边界定义可配置的签名时效、载荷限制和结构化幂等响应，准确字段由告警 Spec 固化。

### 最终方案

采用第二种方案：

- HMAC 输入必须覆盖协议版本、来源 ID、请求时间戳和收到的原始请求体字节；必须先验证原始字节的
  长度与签名，再解析 JSON。密钥通过环境或秘密管理设施注入，支持 key ID 和轮换，不进入源码、
  数据库、日志或响应。
- 请求时间戳相对接收端可信时钟的默认容忍窗口为正负 5 分钟，可配置。超出窗口、签名缺失、
  未知 key ID 或摘要不匹配均按机器认证失败拒绝，不进入告警持久化事务。业务唯一约束仍负责
  窗口内相同外部告警的幂等，不用进程内缓存替代。
- Webhook 原始请求体默认上限为 64 KiB，JSON 最大嵌套深度默认为 16，均可配置；必须以实际读取
  字节数而非仅信任 `Content-Length` 执行限制。超限请求在持久化前拒绝，JSON 还必须满足版本化
  Schema 和顶层对象结构，不能把任意无界 JSONB 直接写入数据库。
- 新接收或已有 `RECEIVED` 告警继续返回 HTTP 202；已有 `PROCESSED` 或 `FAILED` 告警的相同载荷
  幂等重复继续返回 HTTP 200，但响应体必须至少包含稳定 `alertId` 和机器可读的
  `processingStatus`，使调用方能够识别失败或人工重放需求。相同外部 ID 对应不同载荷摘要仍返回
  HTTP 409；准确响应 Schema 和错误码由告警接入 Spec 固化。

### 选择原因

- 时间窗口缩小被窃取签名的可重放范围，数据库唯一约束继续兜底窗口内业务重复。
- 在反序列化和持久化前限制真实字节数与 JSON 深度，能够控制不可信输入的资源消耗。
- 保留幂等重复的 HTTP 200 避免无意义重试，同时用响应体表达真实处理状态。

### 影响范围

- 告警 Webhook 请求头、签名串、密钥轮换和时间同步要求。
- 请求体读取、大小限制、JSON 解析约束、Schema 校验和错误响应。
- 幂等响应 Schema、告警源兼容性以及认证、重放、畸形载荷和失败重复测试。

DEC-013 是 DEC-010 告警接入与幂等响应边界的实现细化。

## DEC-014：告警来源 HMAC 绑定请求方法与目标路径

- 日期：2026-09-22
- 状态：已接受
- 替代关系：细化 DEC-013 的 HMAC 输入；两者不冲突时继续同时适用

### 问题

DEC-013 为告警 Webhook 规定的 HMAC 输入覆盖协议版本、来源 ID、请求时间戳和原始请求体字节。
Spec A 还允许机器告警源通过无请求体的 `GET /incident/v1/alerts/{alertId}` 查询自身告警状态。
如果签名不绑定 HTTP 方法和目标路径，同一来源的有效空请求体签名可以在时间窗口内被重用于其他
`alertId` 或其他空请求体路径，不能证明调用方实际授权了当前请求目标。

### 可选方案

1. 保持 DEC-013 的请求体签名输入不变，接受时间窗口内跨目标重放风险。
2. 取消机器来源状态查询，仅保留人员查询以及提交和幂等重复响应中的状态。
3. 保留机器来源状态查询，并让所有使用来源 HMAC 认证的请求绑定 HTTP 方法、目标路径和请求体。

### 最终方案

采用第三种方案：

- 所有使用告警来源 HMAC 认证的 v1 请求必须使用版本化、无歧义的签名输入，同时覆盖协议版本、
  来源 ID、请求时间戳、规范化 HTTP 方法、规范化目标路径和实际接收的请求体字节。
- HTTP 方法必须规范化为大写。目标路径必须规范化为契约定义的路由路径，并保留影响资源授权的
  目标标识；状态查询路径中的 `alertId` 必须参与签名。准确字节编码、字段分隔和路径规范化规则
  由版本化契约固化，不得依赖存在歧义的字符串拼接。
- 无请求体的方法使用确定的空字节序列作为请求体部分。Webhook 仍签署实际接收的原始请求体
  字节，不得重新序列化 JSON 后再验签。
- 方法、路径、目标标识、请求体或其他已签名组成部分任一不匹配，都必须在返回业务数据或进入
  持久化事务前按机器认证失败关闭。状态查询还必须验证认证来源对目标 Alert 的所有权。
- DEC-013 的正负 5 分钟默认时效、key ID、密钥轮换、秘密材料保护、请求体限制和幂等响应规则
  继续适用；本决策不引入第二套机器认证机制。

### 选择原因

- 将签名绑定到方法和目标资源，可以阻止有效签名在容忍窗口内被跨方法、跨路径或跨 Alert 使用。
- 保留机器来源的自助状态查询，使告警源能够在提交响应丢失或异步处理期间安全对账。
- 复用现有来源身份、密钥轮换和时效规则，比引入另一套服务认证机制更小且更易验证。

### 影响范围

- 告警提交和机器状态查询的签名串、客户端兼容性与版本化契约。
- 方法、路径、目标标识、空请求体和原始请求体字节的规范化与验签顺序。
- 跨方法、跨路径、跨 `alertId`、请求体篡改和时间窗口内重放的安全验收场景。

DEC-014 是 DEC-013 机器认证输入的安全细化；如果两者对签名输入范围的描述不同，以 DEC-014
对所有来源 HMAC 请求的完整绑定规则为准。

## DEC-015：Alert 审计采用独立只追加事实表

- 日期：2026-09-22
- 状态：已接受
- 替代关系：细化 DEC-010 的初期核心表集合与“无逐次 Attempt 历史”边界

### 问题

DEC-010 初期只列出 Alert、Incident、Timeline 和 Outbox 四张核心表，并明确不建立逐次 Attempt
历史。已确认的 Spec A 同时要求对 Alert 接收、终态失败、人工重放接受或拒绝以及恢复为已处理
保留只追加审计事实；这些事实不属于 Incident Timeline，也不能放入默认可清理的 Outbox。计划还
需要确定每条 Alert 恰好关联一个 Incident 时是否新增独立关联表。

### 可选方案

1. 把 Alert 审计事实写入 Incident Timeline，并允许没有 Incident 的 Timeline 行。
2. 把审计历史保存为 Alert 行内 JSON 数组，每次追加时更新 Alert。
3. 新增独立只追加 Alert 审计事实表，并继续由 Alert 行保存唯一 Incident 归属。
4. 同时新增 Alert 审计表和 Alert–Incident 关联表。

### 最终方案

采用第三种方案：

- 初期 Incident 核心表集合扩展为 `t_incident_alert`、`t_incident_alert_audit`、`t_incident`、
  `t_incident_timeline` 和 `t_incident_outbox`，全部由 `incident` 模块独占。
- `t_incident_alert_audit` 只记录 Spec A 已确认的接收、终态失败、人工重放接受或拒绝和恢复事实；
  逐次处理失败、重试调度和 Attempt 明细仍只属于 Alert 当前控制数据、运行状态与安全日志，不进入
  该表。
- Alert 审计事实使用稳定业务事实键防重，只能追加，不提供普通更新或删除能力；安全原因和终态
  失败引用不得包含秘密、完整请求体或堆栈跟踪。
- 每条 Alert 最多归属一个 Incident，因此由 `t_incident_alert` 保存可空 `incident_id`、稳定关联
  事件身份和关联时间，并用内部外键与条件更新保护；初期不新增独立 Alert–Incident 关联表。
- Alert 审计、Incident Timeline 和 Outbox 保持不同语义与保留边界，不互相替代。

### 选择原因

- 独立表能够在 Alert 尚未形成 Incident 时保存不可变审计，又不污染以 Incident 为中心的 Timeline。
- 行内 JSON 追加需要覆盖更新，难以用数据库约束证明只追加与并发正确性。
- Outbox 面向跨领域投递且已发布记录允许清理，不能作为长期审计事实来源。
- 一对多归属直接保存在 Alert 行即可满足唯一关系和稳定事件身份，避免无必要的第六张表。
- 明确排除逐次 Attempt 行，继续遵守 DEC-010 的初期范围控制。

### 影响范围

- Incident 数据模型、全量 Schema、增量升级脚本和 PostgreSQL 约束。
- Alert 接收、终态失败、人工重放、恢复以及验收证据计数。
- Alert–Incident 原子关联、稳定事件身份与并发条件更新。
- Alert 审计、Incident Timeline 和 Outbox 的查询及内容安全测试。

DEC-015 只扩展满足已确认审计义务所需的最小持久化集合，不授权建立通用审计平台、逐次 Attempt
历史或多对多 Alert–Incident 关联。

## DEC-016：同键告警接收与 Incident 封存使用单调可信排序时间

- 日期：2026-09-23
- 状态：已接受（用户确认）
- 替代关系：细化 DEC-010 的确定性聚合和数据库可信时间边界，不改变 DEC-013 至 DEC-015 的认证、审计及表集合

### 问题

普通数据库墙钟可能在并发事务中返回相同值，也可能因时钟调整回拨；现有 Snowflake 风格
`alertId` 不保证按事务提交顺序递增。如果仅按 `(receivedAt, alertId)` 排序，后提交的同键 Alert
可能被排在已经创建的 Incident anchor 之前。解决操作若使用回拨后的墙钟，还可能把解决前已接收
的 Alert 错判为封存后成员。这些情况会破坏 Spec A 的 episode 和生命周期归属确定性。

### 可选方案

1. 继续使用原始数据库墙钟和 `alertId` 决胜，接受 anchor 与封存归属在事后变化。
2. 新增全局接收序号或独立协调服务，并以该序号替代可信接收时间。
3. 在同一聚合键的数据库事务中串行化接收、Incident 聚合和首次解决，使用数据库墙钟与该键已有的最大业务排序时间计算单调时间，不新增表或外部服务。

### 最终方案

采用第三种方案：

- 已认证并校验的首次接收，在持久化事务内以版本化 `aggregationKey` 获取同键数据库事务锁；
  取得锁后读取已提交同键 Alert 的最大 `receivedAt` 和 Incident 已形成的最大生命周期 `sealedAt`，
  将新 `receivedAt` 分配为数据库当前墙钟与上述最大值之后一个时间精度单位两者中的较大者。
  数据库存储精度为微秒，计划产物应规定溢出检查。相同幂等身份的重复请求只读取既有事实，
  不重新分配接收时间。
- 首次解决在同一键的事务锁下分配 `sealedAt`，其值为数据库当前墙钟与此前已提交同键 Alert
  的最大 `receivedAt` 两者中的较大者；解决事务持有该锁直至提交。随后提交的同键首次接收必须
  得到严格晚于该 `sealedAt` 的时间。
- Incident 聚合事务也在同键锁下重算已持久化 Alert 集合、episode 和封存边界，之后才创建或
  关联 Incident。`alertId` 仅作为预置数据中时间相同的确定性决胜键，不承担正常接收顺序保证。
- 同键事务锁只是串行化该键的读取与写入顺序；Alert 幂等、episode 创建、聚合开放唯一性、
  一次性关联和 Timeline/Outbox 防重仍分别由数据库唯一约束、受保护更新及原子事务兜底。
- `receivedAt` 和 `sealedAt` 是数据库边界分配的业务排序时间，可能在墙钟回拨或高密度同键接收
  时略晚于瞬时物理墙钟。来源时间仍只作证据，不参与该顺序；机器签名时效使用独立的可信当前
  墙钟，不用单调化后的业务排序时间替代。

### 选择原因与影响范围

- 不改变 Spec A 的 `(receivedAt, alertId)` 排序、30 分钟窗口或五张核心表，也不引入 Redis
  锁、额外服务或通用序号系统。
- 在同键并发接收、时钟同值/回拨及接收与解决竞争下，可以用真实 PostgreSQL 事务证明 anchor
  与封存边界不会事后逆转。
- 影响 Alert 接收、Incident 聚合与首次解决的事务顺序、计划中的索引/锁策略，以及对应
  PostgreSQL 集成测试。实现阶段须验证同键竞争与锁顺序，不得用进程内互斥替代。

## DEC-017：v1 告警指纹与 Incident episode 聚合规则

- 日期：2026-09-23
- 状态：已接受（用户确认）
- 替代关系：细化 DEC-010 留给后续 Spec 确认的指纹、聚合键和窗口规则；与 DEC-016 的同键时间顺序同时适用，不改写其结论

### 问题

DEC-010 已确定可靠接收、异步聚合与数据库并发仲裁，但没有指定哪些告警属于同一业务身份、
时间窗口如何切分以及何时形成 Incident。若这些规则仅保留在功能文档，后续 Spec 与实现容易对
同一告警得出不同归属。

### 可选方案

1. 只按来源规则 ID 聚合，忽略环境、服务和资源身份。
2. 使用未经版本化的可变字段或来源时间聚合，由 Worker 按物理处理顺序决定 Incident。
3. 固定版本化身份元组、规范化与摘要，并用持久化可信接收顺序、实际窗口和生命周期封存边界划分 episode。

### 最终方案

采用第三种方案，作为 Spec A v1.0 的长期业务基线：

- v1 指纹身份元组依次为 `alert-fingerprint-v1`、认证后的 `sourceId`、`environment`、
  `service`、`resource.type`、`resource.id`、`ruleId`。字段先通过原始长度与 Unicode 校验，
  再进行 NFC 规范化和首尾 Unicode 空白裁剪；除保持大小写敏感的不透明 `resource.id` 外，
  其余身份字段使用与区域设置无关的小写规范值。
- 指纹是该元组无歧义版本化编码的 SHA-256 小写十六进制摘要；v1 `aggregationKey` 为
  `alert-incident-v1:` 加指纹。`externalAlertId`、来源发生时间、标题、摘要、严重度和 labels
  不参与指纹或聚合键。
- 同键全部已持久化 Alert，包括尚未处理或终态 `FAILED` 的成员，按 `(receivedAt, alertId)`
  排序；相邻可信接收时间差大于实际窗口，或跨越已记录的首次生命周期封存边界时，划分新
  episode。正常接收路径的同键排序时间须遵循 DEC-016，不依赖 Worker 调度或来源时钟。
- v1 实际窗口默认 30 分钟，精确边界包含在内且可按部署配置；每个 Incident 保存实际规则版本
  和窗口。同一聚合键最多一个聚合开放 Incident。只有至少一条成员成功处理后，episode 才形成
  唯一 Incident；`PROCESSED` 成员须恰好关联一次，`FAILED` 成员可暂不关联并在授权重放成功后
  按原 episode 归属。窗口结束后才形成的历史 Incident 创建即封存。

### 选择原因与影响范围

- 身份字段、规范化和版本前缀使聚合可解释、可复现，也为以后明确升级规则保留兼容边界。
- 数据库可信接收顺序及持久化边界符合 DEC-010、DEC-016，不把来源时间或 Worker 调度当作事实。
- 本决策影响告警规范化、Incident 归属、聚合开放并发仲裁与验收数据；精确验收场景以
  `specs/001-reliable-alert-incident/spec.md` v1.0 的 FR-015～FR-025、SC-002/SC-003 为准。

## DEC-018：Incident 主状态机与生命周期封存

- 日期：2026-09-23
- 状态：已接受（用户确认）
- 替代关系：细化 DEC-010 留给后续 Spec 确认的完整 Incident 状态转换；与 DEC-017 的 episode 规则及 DEC-016 的封存时间边界同时适用

### 问题

告警聚合和后续审批到模拟处置必须使用同一组 Incident 状态。若合法转换、封存和重开条件没有
长期基线，自动关联或后续 Action 流程可能静默改变主状态，破坏审计与告警归属。

### 最终方案

Incident 从 `OPEN` 创建，仅允许以下主状态转换：

| 起始 | 目标 | 必要条件 |
| --- | --- | --- |
| `OPEN` | `ACKNOWLEDGED` | 授权响应人员 |
| `OPEN` | `RESOLVED` | 授权响应人员及解决原因 |
| `ACKNOWLEDGED` | `MITIGATING` | 授权响应人员，或后续明确授权的处置服务 |
| `ACKNOWLEDGED` | `RESOLVED` | 授权响应人员及解决原因 |
| `MITIGATING` | `ACKNOWLEDGED` | 授权响应人员及缓解停止或失败原因 |
| `MITIGATING` | `RESOLVED` | 授权响应人员及解决原因 |
| `RESOLVED` | `ACKNOWLEDGED` | 授权响应人员、重开原因，且同键不存在较新未关闭 Incident |
| `RESOLVED` | `CLOSED` | 授权响应人员 |

- 未列出的转换全部拒绝；`CLOSED` 为终态。每次请求必须声明预期状态和版本，过期或竞争请求
  返回当前安全状态与版本，不得覆盖胜出者或追加成功 Timeline 事实。
- 自动关联 Alert 不改变主状态。首次进入 `RESOLVED` 时按 DEC-016 形成不可移除的可信
  `sealedAt`，同一事务各追加一条 `INCIDENT_STATUS_CHANGED` 与
  `INCIDENT_AGGREGATION_SEALED` Timeline 事实；后续重新打开或再次解决不重复封存。
- 重新打开只恢复生命周期，不恢复聚合资格；“较新”按
  `(episodeStartAt, episodeAnchorAlertId)` 比较，`RESOLVED` 仍属未关闭。关闭或重开都不得移动
  原有封存边界。

### 选择原因与影响范围

- 完整转换表与版本校验让告警处理、人工操作和后续 Spec B 共用明确的状态语言。
- 永久封存边界避免重开后旧 Incident 重新吸纳新告警；只追加 Timeline 保留可审计事实。
- 本决策影响 Incident 状态转换、Timeline、后续 Action 授权与验收；精确规则以

## DEC-019：Incident 关闭与处置许可原子裁决

- 日期：2026-09-23
- 状态：已接受（用户确认）
- 替代关系：补充 DEC-018 的 `RESOLVED -> CLOSED` 对 Action 的影响；细化 DEC-012 的许可截止检查时钟，其他调度、清扫与 `UNKNOWN` 规则保持适用

### 问题

Spec A 允许授权人员关闭已解决的 Incident，Spec B 则允许先提出和批准 Action。若关闭与审批、
调度或票据消费分别裁决，可能出现 Incident 已关闭但旧许可仍启动模拟副作用。长时间等待数据库锁时，
使用事务开始时刻的时间快照判断票据和授权截止，也可能让实际已过期的许可被消费。

### 最终方案

- Action 只能在未 `CLOSED` 的 Incident 上提出；批准、首次调度、崩溃补票和首次合法票据消费都必须
  重新核对 Incident 当前未关闭。Action 完成不自动改变 Incident 主状态。
- Incident 成功关闭与其尚未开始执行的 `PENDING_APPROVAL`、`APPROVED`、`DISPATCHING` Action 许可失效
  属于同一受保护业务决定：这些 Action 转为 `EXPIRED`；待审批事实转为 `EXPIRED`，已批准事实保留原
  批准记录，尚为 `ISSUED` 的票据失效。每个生效变化追加只追加 Timeline 事实，不改写既有事实。
- 关闭与票据消费以同一 Incident 持久化边界、预期状态/版本及一致的锁顺序互斥裁决。关闭先胜出
  时不得再授予执行许可；消费先胜出时 Action 已为 `EXECUTING`，关闭不得把它推定为未执行。
  已 `EXECUTING` 或 `UNKNOWN` 的 Action 保留回执、超时、只读对账和证据收敛路径，禁止再次启动工具。
- 延续 Spec A 的“同键事务锁（适用时）→ Incident 行锁 → Action/Approval/Execution/Ticket”顺序。
  审批、授权、票据消费、清扫等截止资格在取得所需锁后，以主 PostgreSQL 当时的可信墙钟重新判断；
  PostgreSQL 可使用 `clock_timestamp()`，不得依赖事务开始时固定的 `CURRENT_TIMESTAMP`/`now()`
  作为锁等待后的唯一截止依据。此条细化 DEC-012 所称数据库状态时钟，不改变其绝对截止、票据 TTL
  与 `receiptDueAt` 规则。
- DEC-012 的时间驱动清扫规则继续适用：`DISPATCHING` 且无有效票据、授权仍有效时交给恢复流程，
  仅授权也过期才由时间清扫转 `EXPIRED`。本决策的 Incident 关闭是独立业务转换，不冒充时间清扫。

### 选择原因与影响范围

- 同一持久化决定消除关闭与旧票据消费之间的授权空隙，不要求 MCP Server 复制 Incident 主状态。
- 锁后读取可信当前时间避免把数据库锁等待错误地算成许可仍有效；条件更新和数据库约束继续作为
  并发正确性边界。
- 影响 Spec A 的 Incident 关闭事务、Spec B 的 Action/Approval/Ticket 状态与 Timeline、Worker 领取
  和票据消费，以及关闭/消费/截止竞争的 PostgreSQL 集成验收；不改变 DEC-018 的主状态转换表。

## DEC-020：共享 Timeline/Outbox 的处置扩展与只追加回执历史

- 可重建的 `ragent_bit` 只保存隔离演示资源及其应用记录，不能保存 Action、审批、权威回执、

  不引入通用事件平台、跨库事务或可变 Agent 消息作为安全事实。

  PostgreSQL/跨进程验收；具体设计见 `specs/002-approval-safe-simulation/`，批准计划前不得实施。
